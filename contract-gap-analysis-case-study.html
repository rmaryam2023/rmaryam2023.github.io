AI-Powered Contract Gap Analysis Platform

Role ML Engineer / Team Lead
Timeline 3 months
Impact 80% labor reduction
Company ThreatConnect (Dataminr)
Python LangChain OpenAI GPT-4 RAG AWS Bedrock Vector Databases NLP Prompt Engineering

The Challenge

ThreatConnect was drowning in contract review work. Legal teams spent weeks manually reading through hundreds of vendor contracts, comparing them against internal compliance requirements, and identifying gaps or missing clauses. This process was:

  • Time-intensive: 2-3 hours per contract × hundreds of contracts
  • Error-prone: Human reviewers missed critical clauses or inconsistencies
  • Non-scalable: As the company grew, the backlog grew faster than the team
  • Knowledge-dependent: Only senior legal staff could perform thorough reviews
Core Problem: How do we automate the extraction, comparison, and gap analysis of legal contracts while maintaining the accuracy and nuance that legal work demands?

The Solution

I led the design and implementation of a Generative AI platform that uses Large Language Models (LLMs) with Retrieval-Augmented Generation (RAG) to automate contract analysis. The system works in three stages:

1. Intelligent Document Processing

Built a robust document ingestion pipeline that handles various contract formats (PDF, DOCX, scanned images). Used AWS Textract for OCR when needed, then preprocessed and chunked documents intelligently to preserve legal context.

2. RAG-Based Information Retrieval

Implemented a vector database using embeddings to store our internal compliance requirements and historical contract clauses. When analyzing a new contract, the system:

  • Embeds the contract into the same vector space
  • Retrieves the most relevant compliance requirements
  • Feeds both the contract and requirements to the LLM as context

3. LLM-Powered Gap Analysis

Through extensive prompt engineering, I developed a multi-step prompting strategy that:

  • Extracts all relevant clauses from the contract
  • Compares them against required clauses using chain-of-thought reasoning
  • Identifies missing, incomplete, or non-compliant sections
  • Generates structured reports with specific recommendations

Technical Deep Dive

Prompt Engineering Strategy

The biggest challenge was getting the LLM to be both comprehensive and precise. I developed a multi-stage prompting approach:

  • Stage 1 - Extraction: "Act as a legal analyst. Extract all clauses from this contract related to [category]..."
  • Stage 2 - Classification: Classify extracted clauses into predefined categories using few-shot examples
  • Stage 3 - Gap Analysis: Compare against requirements with explicit instructions to cite specific contract sections
  • Stage 4 - Verification: A separate LLM call validates findings to reduce hallucinations

RAG Architecture Decisions

Key architectural choices that improved accuracy:

  • Used text-embedding-ada-002 for consistent embeddings across contracts and requirements
  • Implemented hybrid search (vector + keyword) to catch exact legal terminology
  • Built a dynamic context window that adjusts chunk size based on contract complexity
  • Added metadata filtering to prioritize relevant precedents (industry, jurisdiction, etc.)

Handling Edge Cases

Legal documents are messy. I implemented several robustness measures:

  • Confidence scoring for each extracted clause
  • Flagging of ambiguous language for human review
  • Versioning system to track changes in compliance requirements
  • Audit trail showing which sections of the contract informed each finding

Results & Impact

80% Reduction in manual labor hours
15 min Average analysis time (down from 2-3 hours)
1000+ Contracts analyzed in first 3 months
95% Accuracy vs. senior legal review

Beyond the quantitative metrics, the system fundamentally changed how the legal team operates:

  • Freed up senior staff: Legal experts now focus on complex edge cases rather than routine reviews
  • Faster contract cycles: Vendor onboarding accelerated by 3-4 weeks on average
  • Knowledge democratization: Junior staff can now perform preliminary reviews with AI assistance
  • Continuous improvement: The system learns from human corrections, getting smarter over time

Challenges & Learnings

Challenge 1: LLM Hallucinations

Early versions would occasionally cite clauses that didn't exist. Fixed this by:

  • Requiring the model to quote exact text with character positions
  • Implementing a verification step that cross-references quotes against source document
  • Adding confidence scores and flagging low-confidence findings for human review

Challenge 2: Domain-Specific Language

Generic LLMs struggled with legal terminology. Addressed through:

  • Fine-tuning on legal document corpus (when possible)
  • Building a legal terminology glossary into the system prompt
  • Using few-shot examples from actual contracts in our domain

Challenge 3: Cost Management

Running GPT-4 on every contract was expensive. Optimizations included:

  • Preprocessing to extract only relevant sections before LLM analysis
  • Caching embeddings and common compliance requirements
  • Using cheaper models (GPT-3.5) for initial classification, GPT-4 only for complex analysis
  • Batch processing contracts during off-peak hours

What I'd Do Differently

Reflecting on the project, a few areas for improvement:

  • Earlier user testing: Built v1 in isolation; v2 needed significant UX overhaul based on legal team feedback
  • More structured evaluation: Should have built a test set of annotated contracts earlier for systematic evaluation
  • Explainability from day one: Added explanation features in v2, but should have been core from the start for legal use case

Key Takeaways

For LLM-based automation projects:

  • Prompt engineering is 50% of the solution. Invest time here.
  • RAG > fine-tuning for most knowledge-intensive tasks (faster iteration, more control)
  • Build verification layers. Never trust a single LLM call for critical decisions.
  • Domain experts are essential. Collaborate closely with end users throughout.
  • Start with a narrow use case and expand. We began with just NDAs before tackling all contract types.
